# User Authentication & Roles (from scratch)

Greenfield design: the app has no authentication today — only a device-local profile switcher. This feature introduces server-authoritative identity (email + password and Google sign-in), email verification and password reset, and a single admin role guarding curated-content writes. Per-user domain data stays on the device: no per-user synchronization is introduced.

## Specs

**S1.** Registration supports email + password and Google sign-in, both against a self-hosted auth server running on our own Hono/Workers API. No third-party auth provider (Auth0, Clerk, Firebase Auth, Supabase Auth).

**S2.** Email verification and password reset are part of v1: signup sends a verification email; a reset request sends a tokenized link; completing a reset revokes all active sessions of that user.

**S3.** Identity is server-authoritative. Better Auth 1.7 owns the schema: `user`, `session`, `account`, `verification` replace the existing `users` table in `packages/shared/src/modules/users/schema.ts`. The server `users` table is empty today, so this is a drop-and-create, not a data migration.

**S4.** The five existing FKs migrate from `users.id` to `user.id`: `tasks.user_id`, `user_question_preferences.user_id`, `user_theme_progress.user_id`, `user_reflections.user_id` (and `user_reflection_items` through `user_reflections`). All are NOT NULL with cascade today; they stay NOT NULL with cascade.

**S5.** Roles use the Better Auth `admin` plugin (`role`: `admin` | `user`, plus `banned`). Authorization is a server-side `requireRole("admin")` middleware. `role` is read from the session only, never from a request body. The first admin is created by a seed script, never by an endpoint.

**S6.** All curated-content write endpoints require the admin role: `POST/PUT/DELETE /v1/readings` and `POST /v1/authors`. Reads stay public. Today every one of these writes is fully anonymous.

**S7.** The anonymous `POST /v1/users` and the unfiltered `GET /v1/users` are removed. User listing is served by the admin plugin's endpoints, which are admin-only.

**S8.** Session transport is chosen per client class, not per provider. A non-browser client (native app, CLI, future integration) sends `Authorization: Bearer <session token>`, and the token comes from the `set-auth-token` header of a JSON auth response, stored per S22 and injected through the existing `HttpClientConfig.getAuthToken` (`apps/mobile/src/infrastructure/http/http-client.ts`). A browser keeps the cookie Better Auth sets and needs no token handling of its own; S26 covers that posture. Federated sign-in never returns by redirect on a non-browser client: the provider's ID token is exchanged through `signIn.social({ provider, idToken })`, which is a normal JSON request, so the bearer header arrives exactly as it does for password sign-in. The Expo cookie-in-URL flow (`@better-auth/expo` and its `?cookie=` parameter) is rejected: a session credential must never travel in a URL.

**S9.** Tokens are stored in `expo-secure-store` on the device, never in `expo-sqlite`.

**S10.** Per-user data (`tasks`, `user_reflections`, `user_reflection_items`, `user_theme_progress`, `user_question_preferences`) stays device-local. Out of scope, explicitly: server tables for them, push in the sync engine, conflict resolution, per-user encryption. The sync engine continues to push/pull curated content only.

**S11.** There is no local claim and none is needed. Both seeds write one shared fixed `DEMO_USER_ID` — the server seed creates that identity with a real hashed credential outside production, the device seed writes the same row — so a demo sign-in already owns the seeded content. Rows keyed to the other seed profiles stay owned by those profile ids, and no user id is ever remapped at sign-in. This supersedes the original claim requirement (see L16).

**S12.** `reading_logs` gains a `user_id` column. Read history is currently global on both server and device; device history must be attributable to the signed-in user.

**S13.** The client replaces `src/context/auth-context.tsx` with a session provider exposing `session.user`, and gains four surfaces: a sign-up form (email + password), a sign-in form carrying a Google button, a password-reset screen reached through a deep link that carries the token, and a verification landing screen that reports whether the token verified or expired. Settings keeps a sign-out action replacing the profile switcher. `currentUser` used for local writes becomes `session.user.id`.

**S14.** Workers configuration must satisfy Better Auth's constraints in the version actually installed (1.7.28): `compatibility_date` at or above `2025-04-01` so `process.env` is populated; `advanced.ipAddress.ipAddressHeaders: ["cf-connecting-ip"]` in its flat shape, because the nested `config.ipAddressHeaders` shape is silently ignored and the auth rate limiter then collapses into one bucket; and background dispatch wired through the request execution context (`c.executionCtx.waitUntil`, reached through AsyncLocalStorage) rather than a static `cloudflare:workers` import, so verification and reset emails are never awaited and the Bun test runner can still load the module.

**S15.** CORS moves from the current wildcard to an explicit origin allowlist with credentials.

**S16.** The email sender sits behind a single internal interface so the vendor is a detail. Until a vendor is chosen, the development implementation logs the verification/reset link and writes it to a file, mirroring Cloudflare's local `send_email` behaviour. Vendor decision is open: Cloudflare Email Service requires a domain whose DNS is on Cloudflare and Workers Paid for arbitrary recipients; Resend requires a verified domain on any DNS host.

**S17.** Tests assert, for each write endpoint in S6: 401 without a session, 403 with a non-admin session, 2xx with an admin session, and that a rejected request leaves stored content unchanged. Plus: sign-up over HTTP yields an id accepted by the domain `User`; Bearer session resolution works and a wrong password creates no session; the seeded admin can sign in and holds the admin role; Google sign-in against a mocked IdP; reset revokes existing sessions; and the mobile surfaces: sign-up creates an account, a reset deep link sets a new password, an expired verification token reports failure instead of success, and sign-out clears the stored session.

**S18.** Turso + Drizzle adapter compatibility is unverified (no official documentation; the Better Auth demo uses Kysely for Turso). This is proven or disproven before any product schema change (T1).

**S19.** A document in `odd/tasks/` may stay open across intermediate commits by declaring `- **Status**: open`. `scripts/check-odd.sh` then skips the closed-document requirements for that file only; any other document still fails when it has pending tasks or lacks a `- **Completion & Delivery**:` line. Closure replaces the open declaration with the completed tasks and the delivery record, so the escape cannot outlive the feature.

**S20.** Exactly one admin exists after seeding: the seed creates a dedicated admin identity with `role: "admin"` through Better Auth, outside production, with a documented credential, and no endpoint can grant the admin role. Without it, enabling S6 would leave the app with nobody able to write curated content.

**S21.** Device read history becomes attributable: every new insert into `reading_logs` on the device writes the current `session.user.id`, while rows written before sign-in stay NULL and are never backfilled. The sync engine's `reading_log` branch stays a no-op.

**S22.** Token storage is per platform and no path may assume one exists. Native stores the session token in `expo-secure-store`, never in `expo-sqlite`. Web has no SecureStore, so the browser relies on its own cookie jar and no web code path may call the storage module; a shared module that touches storage branches on platform explicitly. The web build never keeps a session token in local storage.

**S23.** v1 does not require a verified email to sign in: `requireEmailVerification` stays off because S16's sender is still the development implementation, and enforcing verification before a real sender exists would lock every signup out. Turning it on is a separate change gated on a delivered sender.

**S24.** Google account linking is explicit: a Google sign-in must never silently take over an existing password account whose email is unverified. If the library cannot express that guard, implicit linking stays disabled and the user gets an error instead of a takeover.

**S25.** Session lifetime is explicit rather than inherited: the session row carries an expiry, the effective default lifetime is recorded here when T6a lands, and a password reset revokes every session of that user (S2). v1 adds no sliding-window refresh; adding one later is a documented change with its own spec.

**S26.** The web session is a cookie, so web carries CSRF surface a bearer client never has. The cookie is `HttpOnly`, `Secure` outside local development and `SameSite=Lax`; CORS is an explicit origin allowlist with credentials and never a wildcard; and a state-changing request from the web target is covered by the library's origin check or an explicit CSRF guard. T5 stops being hygiene and becomes this requirement.

**S27.** Apple sign-in is the next federated provider, and the foundation must accept it as configuration rather than redesign: the same `signIn.social({ provider: "apple", idToken })` path as S8, provider configuration on the server only, the button shown where the platform supports it and hidden where it does not. Four costs are accepted explicitly. (a) Apple's client secret is a JWT signed with a `.p8` key that expires on a schedule and must be rotated, unlike Google's static secret. (b) Apple returns name and email only on the first authorization, so profile creation must accept a missing name and derive a fallback from the email local part instead of failing its own validation. (c) The email may be an Apple private relay address: valid and unique, but not the user's real inbox. (d) App Store guideline 4.8 makes Apple sign-in mandatory once third-party social login ships on iOS.

**L26** (user decision after re-evaluation, verbatim: "recodemos que estamos en MVP y podemos cambiar todo, queremos solidas bases para hacerlo crecer, reevalemos"): the transport contract was re-decided on foundation criteria rather than MVP speed, and S8, S22 were rewritten while S25, S26 and S27 were added.

Why the change: `@better-auth/expo` does not store a token at all, it stores the session cookie in SecureStore and returns the OAuth session through a `?cookie=` parameter on the deep link. Two things rule it out as a foundation. First, a session credential in a URL leaks through channels a header does not (history, deep-link logs, referrers). Second, if the app scheme is missing from `trustedOrigins` the session simply does not arrive and nothing reports an error, which is the exact silent-failure class this feature keeps eliminating. Verified in the library source and docs, not assumed: the client plugin persists cookies only, and the server hook attaches the cookie to the redirect solely for trusted origins.

What replaces it: the provider's ID token is exchanged through `signIn.social({ provider, idToken })`, a normal JSON request, so `set-auth-token` comes back the same way it does for password sign-in and the client keeps one transport (the bearer hook that already existed and was never wired). This generalises: any platform able to obtain a provider ID token joins without a new server endpoint, and the server gains provider configuration only.

The decision that actually settled it was Apple. App Store guideline 4.8 requires Apple sign-in as soon as third-party social login ships on iOS, and with the ID-token path Apple is another provider on the same call, while the redirect-plus-cookie path would need per-provider native integration plus the same plugin surface. A foundation that cannot absorb Apple cheaply is not a foundation for an iOS product.

Accepted costs, recorded rather than hidden: native configuration per platform (client IDs, a development build), and for Apple specifically a client secret that is a JWT signed with an expiring `.p8` key and must therefore be rotated on a schedule. Also recorded as a design constraint on today's work rather than Apple's task: profile creation must accept a missing name and derive a fallback from the email local part, because Apple hands name and email over only once and the user may decline, and our own validation currently rejects a blank name. Chosen fallback: derive from the email local part, because a listing of dozens of identical placeholders is worse than an approximate name.

Rejected outright: `@better-auth/expo`, the `expo()` server proxy endpoint, and origin override. Not rejected for effort, but because none of them is needed to reach Apple, web and future clients, and each adds permanent server surface.

**The new gate state — `unavailable`.** `deriveSessionGate` now returns one of four states, in this order: `loading` (the stored session is still being restored, or a retry is), `authenticated` (a user was resolved), `unavailable` (the restore could not judge the stored credential: offline, past its deadline, or a server-side failure), `unauthenticated` (the credential was rejected, or the server explicitly answered "no session"). `unavailable` is the state this task adds: **the token is kept, the auth tree is not opened, and the surface offers a retry plus a way to sign in anyway.** It is derived from `SessionRestoreProblem { reason: "offline" | "timeout" | "server-error"; message }`, which the provider exposes as `restoreProblem` next to `user`, `isLoading`, `retryRestore()` and `signInAnyway()`. `unavailable` renders `SessionUnavailableScreen` (`testID="session-unavailable-screen"`), a full-screen state with the reason as its description, a primary "Try again" and a secondary "Sign in anyway"; the second only leaves the retry state — it clears no token, because the credential is still the user's and a successful sign-in overwrites it. **The defect.** The slot was per client instance: cleared at the start of every `call`, written by the response hook, read by the `call` that was awaiting its operation. With two calls open, the second call's clear erased the first call's failure, and a failure written by one call was read by whichever call reached its read next. Observable harm: one failed keychain write could make a later, correctly answered sign-in or sign-up report `SESSION_TOKEN_STORAGE_FAILED` and be blocked, where the baseline accepted it. The docstring admitted the ambiguity ("if a write fails while two calls are in flight, both report the local failure"); that sentence is deleted, because it is no longer true, and so is the slot.

**The fix — the failure belongs to one call, by construction.** `call` now creates its own `TokenWrite` (`{ failure, onSuccess }`) and hands `write.onSuccess` to its own request as a per-request fetch option — `client.signIn.email(body, { onSuccess })`, `client.signUp.email(body, { onSuccess })`, `client.getSession({ fetchOptions: { onSuccess } })` — which Better Auth merges into that one request and awaits before it resolves. The recorded reason therefore only ever reaches the call whose response carried `set-auth-token`: no call can observe a failure it did not cause, because there is no longer any state for it to observe. `signOut()` keeps no write hook: a sign-out response has no credential worth persisting, and the service clears the token immediately after it. The rejected alternative was the monotonic call id with a `{ callId, failed }` record: the response hook cannot learn which call id its request belongs to when the answer arrives (a call starts before its request is built, and two calls interleave before either reaches the fetch), and a conservative version that refuses to attribute when two calls are open would drop exactly the failure the criterion requires call A to keep reporting. The per-request hook is the correlation the library already provides.
