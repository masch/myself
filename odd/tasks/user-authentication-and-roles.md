# User Authentication & Roles (from scratch)

Greenfield design: the app has no authentication today — only a device-local profile switcher. This feature introduces server-authoritative identity (email + password and Google sign-in), email verification and password reset, and a single admin role guarding curated-content writes. Per-user domain data stays on the device: no per-user synchronization is introduced.

- **Status**: open

## Specs

**S1.** Registration supports email + password and Google sign-in, both against a self-hosted auth server running on our own Hono/Workers API. No third-party auth provider (Auth0, Clerk, Firebase Auth, Supabase Auth).

**S2.** Email verification and password reset are part of v1: signup sends a verification email; a reset request sends a tokenized link; completing a reset revokes all active sessions of that user.

**S3.** Identity is server-authoritative. Better Auth 1.7 owns the schema: `user`, `session`, `account`, `verification` replace the existing `users` table in `packages/shared/src/modules/users/schema.ts`. The server `users` table is empty today, so this is a drop-and-create, not a data migration.

**S4.** The five existing FKs migrate from `users.id` to `user.id`: `tasks.user_id`, `user_question_preferences.user_id`, `user_theme_progress.user_id`, `user_reflections.user_id` (and `user_reflection_items` through `user_reflections`). All are NOT NULL with cascade today; they stay NOT NULL with cascade.

**S5.** Roles use the Better Auth `admin` plugin (`role`: `admin` | `user`, plus `banned`). Authorization is a server-side `requireRole("admin")` middleware. `role` is read from the session only, never from a request body. The first admin is created by a seed script, never by an endpoint.

**S6.** All curated-content write endpoints require the admin role: `POST/PUT/DELETE /v1/readings` and `POST /v1/authors`. Reads stay public. Today every one of these writes is fully anonymous.

**S7.** The anonymous `POST /v1/users` and the unfiltered `GET /v1/users` are removed. User listing is served by the admin plugin's endpoints, which are admin-only.

**S8.** Bearer-token sessions (`bearer` plugin): the native client authenticates with `Authorization: Bearer <session token>` and the returned `set-auth-token` header, which connects to the already-existing `HttpClientConfig.getAuthToken` (`apps/mobile/src/infrastructure/http/http-client.ts`). Cookies remain the transport for the web target only.

**S9.** Tokens are stored in `expo-secure-store` on the device, never in `expo-sqlite`.

**S10.** Per-user data (`tasks`, `user_reflections`, `user_reflection_items`, `user_theme_progress`, `user_question_preferences`) stays device-local. Out of scope, explicitly: server tables for them, push in the sync engine, conflict resolution, per-user encryption. The sync engine continues to push/pull curated content only.

**S11.** Because local rows are keyed by a locally generated user id, the first successful sign-in performs a one-time local claim: `UPDATE user_id` from the previous local id to the server `user.id` in every affected local table. No user's local history is orphaned or lost.

**S12.** `reading_logs` gains a `user_id` column. Read history is currently global on both server and device; device history must be attributable to the signed-in user.

**S13.** The client gets a sign-in screen and a session gate in the root layout, replacing `src/context/auth-context.tsx` with a session provider exposing `session.user`. `currentUser` used for local writes becomes `session.user.id`.

**S14.** Workers configuration must satisfy Better Auth's documented constraints: `compatibility_date` at or above `2025-04-01` so `process.env` is populated (current value is `2025-02-01`), `advanced.ipAddress.config.ipAddressHeaders: ["cf-connecting-ip"]` (Workers do not send `X-Forwarded-For`; without this the auth rate limiter collapses into one bucket), and `advanced.backgroundTasks.handler` wired to `waitUntil` from `cloudflare:workers` so verification and reset emails are sent after the response (not awaited, to avoid timing attacks).

**S15.** CORS moves from the current wildcard to an explicit origin allowlist with credentials.

**S16.** The email sender sits behind a single internal interface so the vendor is a detail. Until a vendor is chosen, the development implementation logs the verification/reset link and writes it to a file, mirroring Cloudflare's local `send_email` behaviour. Vendor decision is open: Cloudflare Email Service requires a domain whose DNS is on Cloudflare and Workers Paid for arbitrary recipients; Resend requires a verified domain on any DNS host.

**S17.** Tests assert, for each write endpoint in S6: 401 without a session, 403 with a non-admin session, 2xx with an admin session, and that a rejected request leaves stored content unchanged. Plus: signup → verification link → verified; login; Google sign-in against a mocked IdP; password reset revokes existing sessions; first-sign-in claim preserves pre-existing local rows.

**S18.** Turso + Drizzle adapter compatibility is unverified (no official documentation; the Better Auth demo uses Kysely for Turso). This is proven or disproven before any product schema change (T1).

**S19.** A document in `odd/tasks/` may stay open across intermediate commits by declaring `- **Status**: open`. `scripts/check-odd.sh` then skips the closed-document requirements for that file only; any other document still fails when it has pending tasks or lacks a `- **Completion & Delivery**:` line. Closure replaces the open declaration with the completed tasks and the delivery record, so the escape cannot outlive the feature.

**`generateId` and its proof.** `advanced.database.generateId: () => crypto.randomUUID()` is set, and the requirement was proven the way L14 asked: with the override removed, an HTTP sign-up returned `user.id = "VvL1EalaxJFqMKgErFEloazDwx43kc8s"` (32 characters, not a UUID) and the integration test failed; with the override in place the same request returns a UUID that `entityIdSchema` accepts, that `mapUserRow` maps without throwing, and that `GET /v1/users/{id}` accepts as a path param. Both states are recorded because only the failing one shows the override is load-bearing. Note for T3/T4: the override applies to every model, so `session.id` and `account.id` are UUIDs too.

**`ipAddressHeaders` shape (deviation from S14's literal text).** Better Auth 1.7.28 reads `advanced.ipAddress.ipAddressHeaders`; the nested `advanced.ipAddress.config.ipAddressHeaders` written in S14 is accepted into `auth.options` but never read by `getIP` in `@better-auth/core`, so it silently falls back to `x-forwarded-for` and then to the localhost/dev fallback. Proven both ways: with the nested shape a request carrying `cf-connecting-ip: 203.0.113.7` stored `session.ip_address = "127.0.0.1"`, with the flat shape it stores `203.0.113.7` (Bun) and `198.51.100.9` (workerd). The implementation uses the flat shape; the intent of S14 (Workers do not send `x-forwarded-for`, so the rate limiter must not collapse into one bucket) is satisfied exactly.

**`backgroundTasks` wiring, and one deviation.** `advanced.backgroundTasks.handler` hands the promise to the request's `ExecutionContext.waitUntil` instead of a static `import { waitUntil } from "cloudflare:workers"`, because that specifier cannot be loaded by the Bun test runner that runs this suite. The context travels from Hono's `c.executionCtx` through an `AsyncLocalStorage`, which keeps it per-request instead of in a module-level variable that concurrent requests would overwrite. Without a context (local Bun dev, tests) the task still runs, unattached to a request lifetime, and a rejection is logged instead of surfacing as an unhandled rejection. Tests assert the promise is handed to `waitUntil` unresolved, and that the no-context path neither throws nor leaks a rejection.

**Workers runtime hashing — POSITIVE (residual (a) from L10 is closed).** `turso dev` (sqld on 127.0.0.1:8099, the same HTTP/Hrana transport as remote Turso) with the repo's own migrations, plus `wrangler dev` on port 8799 running real workerd under `compatibility_date: 2025-04-01` and `nodejs_compat`. One `POST /api/auth/sign-up/email` returned 200 with `set-auth-token` and `user.id = eae720a9-5025-4950-83bd-d76025aec4bb`; the stored `account.password` was 161 characters with the `:` separator at index 32 — byte-for-byte the scrypt format Bun produced in L10 — written by workerd itself. `POST /api/auth/sign-in/email` with the same password returned 200 (so workerd also verifies), a wrong password returned 401, and `GET /api/auth/get-session` with `Authorization: Bearer <set-auth-token>` returned the user. So Better Auth's default scrypt-over-`node:crypto` hashing works under `nodejs_compat`; no fallback hasher is needed. Scope of that claim: `wrangler dev` is local workerd, not a deployed Worker, and `turso dev` is local sqld, not Turso cloud (residual (b) from L10 stands, unchanged).

**Session column observations (from the real DDL and real inserts).** `session.updated_at` is `integer NOT NULL` with **no** database default, and Better Auth populates it on insert: observed `created_at = updated_at = 1795570103355` for a fresh session, and both read back as `Date` through the Drizzle `timestamp_ms` mapping. The session token is **not** stored verbatim relative to the response header: `set-auth-token` is `<32-character token>.<base64 HMAC>`, while `session.token` holds the bare 32-character token. The raw stored token is also accepted as `Authorization: Bearer <raw>`, and a token with a tampered signature is rejected (`get-session` returns `null`), so the signature is over the token, not part of it. Consumers (T6) must persist the header value as received; T4 must not assume the column matches the header.

**`compatibility_date` 2025-02-01 → 2025-04-01, verified harmless.** The Bun suite never reads `wrangler.jsonc`, so the meaningful check was on workerd itself: the same seven requests (health, `/v1/authors` with body, `/v1/users`, invalid-uuid `/v1/users/not-a-uuid`, `/doc`, unknown path, and an auth wrong-password sign-in) were run against two `wrangler dev` instances, one on the old date and one on the new date, against the same database, and `diff` reported **no difference** (200 / 200 with identical pagination body / 200 / 400 / 200 / 404 / 401). **`/api/auth/*` mount consequence.** The handler is registered with `app.on(["GET", "POST"], "/api/auth/*")` directly on the root app, outside the `/v1` sub-app and without OpenAPI metadata. Consequences, both pinned by tests: `POST /v1/auth/sign-up/email` is 404 (auth is unversioned), and `/doc` contains no `/api/auth` path (Better Auth owns its own contract, so our OpenAPI document is not the authority for those endpoints and no generated client will see them). This also means the operation is not part of the `/v1` repositories middleware, so auth routes never touch `authorRepo`/`readingRepo`/`userRepo`.

**Config plumbing.** `ApiBindings` gained `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`; `getProcessEnv()` maps all four and `AppConfig.auth` exposes `{ secret?, baseUrl, google? }` through a `resolveAuthConfig` helper. `baseUrl` defaults to `http://localhost:8787`; Google is described only when both values are present, so a checkout without Google credentials boots and simply has no provider (asserted by introspection of `auth.options.socialProviders`). `apps/api/.dev.vars.example` documents all four with placeholders and states that deployment sets them with `wrangler secret put`; nothing was added to `wrangler.jsonc` `vars`, which keeps `ENVIRONMENT` as the only committed variable. The demo identity contract holds: the seeded account signs in over HTTP with `DEMO_USER_EMAIL`/`DEMO_USER_PASSWORD` and resolves to `DEMO_USER_ID`.
