# Barter Shareable Search

## Objective

The gondola view — search text, certification filter, distance ceiling and the active producer — travels in the URL, so the address a producer is looking at reproduces the same page on another phone, and the browser back button reverts a search instead of leaving the screen.

## Specs

- **S1** — The user asked, verbatim: _"hay algo que en web android me gustaria arreglar a nivel de componente. Cuando apreto en un input se levante el traclado, si apreto para atras de android se cierra el teclado y si apreto para atras de nuevo se podría revertir la busqueda para cada caso? como se podria resolver a nivel de componente?"_
- **S2** — The user's rule, verbatim: _"quisiera consistencia y lo que quisiera también es que la URl que esta viendo el usuario la pueda compartir asi otro usuario puede navegar hasta la misma pagona, se puede ambas?"_ — one mechanism on both platforms, and the address is shareable.
- **S3** — The delivery decision, verbatim: _"Apilalo sobre #119 ahora"_ — this branch is stacked on `fix/web-keyboard-inset`.
- **S4** — The URL is the source of truth for `q`, `tipo`, `km` and `producerId` on both platforms. `producerId` was already read at bootstrap (`barter-store.ts:450-465`, `_layout.tsx:136`); the missing half is state → URL.
- **S5** — History policy: exactly one entry per search, not one per keystroke. Back pops to the address that still carries the pre-search gondola.
- **S6** — A shared, stale or hand-edited link never breaks the screen: an unknown certification, a non-positive distance and an empty query fall back to the persisted gondola, and an unfiltered gondola serialises to no parameters at all.
- **S7** — One gondola instance only. Pushing the same route mounted a second screen and the two instances fought over the URL, each writing its own view; that approach was measured, discarded and recorded below.

## Evidence & Verification

- **TASK-1** — `apps/mobile/src/features/barter/gondola-params.ts` with 16 pins in `__tests__/gondola-params.test.ts`: a full view read out of the URL, the screen's own values kept when the URL says nothing, an unknown `tipo` ignored, `ALL` accepted as an explicit clear, a distance any build might have written (`km=120`), non-positive distances ignored, a repeated parameter taking its first value, an unfiltered gondola writing nothing, whitespace trimmed out, `ALL` never written, zero and negative distances never written, and a round-trip.
- **TASK-2** — `use-gondola-params.ts`. The load-bearing rule, learned the hard way: **each side reacts only when the other moved.** Comparing both directions against the same "current view" made the screen reset on every keystroke — the apply effect read the user's freshly typed text as a divergence and reverted it, so `fill("queso")` left an empty input behind (observed with an instrumented run: `APPLY` fired between two `WRITE`s until the value bounced back to empty). Three more facts came out of the same instrumentation: writing the address before the first frame throws `Attempted to navigate before mounting the Root Layout component` (the gate is `useRootNavigationState().key` plus one `requestAnimationFrame`); `router.setParams({q: undefined})` and `router.replace` both **ignore** `undefined` instead of removing the key, so removals go through `history.replaceState` with the exact set of present parameters (web only — native has no address bar to clean); and `router.push` to the same route mounts a second gondola.
- **TASK-2 (discarded approach)** — `push` of the same route was the user's first choice and it was measured, not assumed: after the first keystroke the log showed `WRITE {q,q}` → `APPLY q=q` → `APPLY "" screen: q=q` → a third instance mounting, and the DOM held two search inputs with values `["", "queso"]`. The hidden instance kept writing its empty view over the URL, which erased what the visible one had just typed. A single instance with one pushed history entry (`pushState` carrying the pre-search address) gives the same back behaviour without the fight. Accepted cost, recorded in the hook: when the search is cleared with the ✕ instead of the back button, the pushed entry stays, so one back press lands on the same gondola. Popping it from the hook was tried and reverted — `history.back()` raced the router's write and left the address holding the query it was supposed to remove, which broke clearing altogether.
- **TASK-3** — `barter.tsx` wires the hook and keeps the URL canonical (the first write fills in `producerId`). The compact search layout is now keyed on **the query, not on focus**: collapsing on focus moved the header on every blur, and with a press in flight the pressed node could be replaced between pointerdown and pointerup. A stable header while a search exists costs one jump on the first character and buys presses that always land.
- **TASK-4** — `apps/mobile/src/components/icon-button.tsx`. Found while chasing why the ✕ never fired: on the web, react-native-web's `Pressable` rejects the press against the hit rect it derives from `hitSlop`, so every `IconButton` in the app was a dead target — the gondola's ✕, the settings rows, the reading cards. The proof took four probes: the element was a real `<button>` with `pointer-events: auto`; `pointerdown`/`pointerup`/`click` all landed **inside** it (`top.closest('[data-testid]')` matched the button); neither `onPress` nor `onPressIn` ever ran, and `el.click()` did not either; a plain `Pressable` at the same spot worked, and the same `IconButton` without `hitSlop` worked too. `hitSlop` is now passed only where it is honoured. This is why TASK-5's clear-address case could not pass before it.
- **TASK-5** — `e2e/barter-gondola-shareable-search.spec.ts`, 4 specs, all green: typing puts the query in the address and a reload keeps the filtered list; a shared `?producerId=sabado&q=queso&tipo=ORGANIC&km=250` reproduces the same producer (revealed by clearing, because a search hides the producer card), the same query, the same count and the same filters in a **fresh browser context**; back reverts the search, keeps the producer and leaves no `q` in the address; clearing with the ✕ leaves a clean address. The keyboard spec's compact-layout case was rewritten to match TASK-3 and now also presses the ✕.
- **TASK-6** — `make check-tests` (mobile 641 pass, 0 fail), `make check-types`, `make check-lint`, `make check-format`, `make check-odd` and the full `make check-e2e-web` — see the delivery note for the final numbers.
- **Completion & Delivery**: Complete on branch `feat/barter-shareable-search`, stacked on `fix/web-keyboard-inset` (#119) as the user asked, in three work-unit commits: the icon-button web fix on its own (it is a separate, pre-existing defect with its own reach), the feature with its unit and browser specs, and this document. Not delivered here, and deliberately: the native hardware back button does not revert the search — on native the URL is the deep link and the back button pops screens, which is a separate `BackHandler` mechanism. Push, PR and merge stay the user's decisions.
